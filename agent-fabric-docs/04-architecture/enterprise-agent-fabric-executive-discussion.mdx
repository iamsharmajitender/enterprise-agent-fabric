# Enterprise Agent Fabric — the idea

One front door → central security, governance, audit, observability, and evaluation → many domain-owned specialised AIs.

The idea is a **common operating model** for AI that acts: one governed ingress, specialised capabilities underneath, controls that exist once for the portfolio.

---

## 1. Architecture

One governed ingress. Chat and jobs enter only through **Agent Fabric Front Door**. The **Agent Fabric Plane** (Control Plane + Data Plane + Capability Registry) decides the path. **Agent Fabric Runtime** does the work. **Shared** holds Memory, RAG, and Tools. **Audit** and **Observability** sit under every run.

Channels never dial domain runtimes. Users do not pick chatbots. High-risk paths do not get side doors. Centralise controls; keep intelligence in domains.

### How the boxes fit together

| Band | Boxes | Job |
| --- | --- | --- |
| Ingress | Chat AFD · API AFD (one contract; two fleets at scale) | Authenticate, entitle, freeze, start |
| Plane | ACP · Data Plane · Capability Registry | Catalogue, classify, publish capabilities |
| Run | Runtime (per activation target) | Pin hydrate, Patterns 0–3, call Shared |
| Shared | Memory · RAG · Tools / PEP | Session memory, retrieve, dual-checked actions |
| Evidence | Audit · Observability · Dashboard | Prove what happened; operate the fleet |

## 2. One request (chat and jobs — same path)

Every request — interactive chat or automated job — follows the same path:

1. **Ask** — User or system calls the Front Door.
2. **Verify** — Identity and entitlement (claims ∩ channel; chat also requires chat-visible).
3. **Route** — Intent under policy (`route` / `clarify` / `abstain`). Jobs name the route: no classifier contest, no clarify — missing claims **fail closed**.
4. **Freeze & start** — Only on `route`: pin version + agent identity, async-start Runtime. Chat gets a slim reply (no routing internals). Jobs get `202` + correlation id.
5. **Execute** — Domain AI runs with approved knowledge and tools under the freeze.
6. **Control & audit** — Pause, approval, or hand-off for high-risk actions; outcome returned; evidence retained.

Clarify and abstain **never** start work. Chat and jobs share the contract; at scale they are separate Front Door fleets so one cannot take the other down.

## 3. What the idea solves

AI that **acts** (customer data, money, regulated processes) is a different problem from a standalone chatbot. If each capability builds its own entry point, security model, approval path, and audit trail, the same enterprise plumbing is rebuilt many times — with different gaps and no single place to answer what happened.

The Fabric idea: the **safe path is the default path**.

### Fragmentation it replaces

Capabilities emerge independently (employees, customers, partners). Teams solve the visible assistant and often rebuild the invisible work: who can access it, how requests are directed, what the AI may do, how actions are approved, and how we prove what happened.

Without a shared model, these questions have no single answer:

- **Who** was allowed to use this AI?
- **What** was it permitted to do?
- **Why** was this capability chosen, and what did it actually do?

Controls that should exist **once** for the portfolio are missing: one audit trail, one operational view, one security model, one kill switch, one approval path, one release bar.

### What the Fabric standardises vs what domains keep

| Fabric holds (once) | Domains keep |
| --- | --- |
| **Security** — identity, entitlement, least-privilege for users and agent principals | Business problems and domain knowledge |
| **Governance** — policy, approval gates, rules for high-risk actions | Models, prompts, specialist logic |
| **Audit** — who asked, what was decided, what ran, who approved | Outcomes and product UX |
| **Observability** — ops view across capabilities | Choice of runtime behind the activation target |
| **Evaluation** — routing goldens and adversarial cases before ship | |

> Centralise controls. Keep intelligence in domains.

### Tensions the model accepts

| Tension | How the idea handles it |
| --- | --- |
| Data privacy | Restrict data flows; least-privilege; data minimisation |
| Unsafe model behaviour | Pre-release evaluation; canarying; human-in-the-loop on risky flows |
| Latency / UX | Policy gating on the decide clock; long loops off that clock; fast-paths for low-risk |
| Shared vs specialised | Platform owns controls; domains own intelligence behind one contract |

## 4. Roles and responsibilities

| Component | Owns | Does **not** own | If it dies |
| --- | --- | --- | --- |
| **Chat / channel frontends** | UI, chips, slim replies | Route table, tools, policy enforcement | That UI down; API path still works |
| **Agent Fabric Front Door (AFD)** | Only public ingress. Authenticate, entitle, call decide, **freeze** route pin, **async-start** Runtime, slim chat / `202` jobs. Two fleets at scale (Chat + API), one contract. | Classify logic; agent loop; catalogue UI | Chat fleet down ≠ jobs fleet down (at scale) |
| **Agent Data Plane (ADP)** | Versioned catalogue + **decide** (`route` / `clarify` / `abstain`). Eligible set = claims ∩ channel. Eval golden surface for misroutes. Serves pinned catalogue row to Runtime. | Pin; start Runtime; tool invoke | Classify fails closed — no silent start |
| **Agent Control Plane (ACP)** | Operator catalogue **UI** / control surface; policy and version visibility | Hot-path decide; start Runtime; channel traffic | Operators blind; in-flight runs continue |
| **Agent Fabric Capability Registry** | Immutable published capabilities `id@version`. Manifests Runtime hydrates at pin. Agent-start tools point at API Front Door, not callee Runtime URLs. | Decide; pin; permit at tool invoke | New runs cannot hydrate; in-flight pins keep schemas |
| **Agent Fabric Runtime (AR)** | Pin hydrate, Patterns 0–3 (single inference → autonomous → deterministic → guided), call Shared. Workload identity ≠ user ≠ agent robot. May be Fabric Runtime **or** another activation (for example a Bedrock Agent) behind the pinned activation target. | Channel ingress; re-decide against live `active`; widen scopes after freeze | Controlled error after accept — not a fake success |
| **Shared — Memory** | Short / long-term memory keyed by session | Ingress classify | Runs degrade; routing still works |
| **Shared — RAG** | Corpus retrieve for grounding | Ingress classify | Grounding degrades; routing still works |
| **Shared — Tools / PEP** | Actions scoped by pinned manifest. **Dual check:** user entitlements (or approval) **and** agent scopes | Route choice; mint freeze | Side effects stop |
| **Agent Audit (data + control)** | Append-only evidence chain; examiner view by correlation id. Default-deny raw utterance, claims, and tokens in payloads. | Block the hot path; replace ops dashboards | New events may drop (fail-open); runs continue |
| **Observability** | Traces, metrics, logs across Front Door, Plane, Runtime, Shared | Compliance evidence store (that is Audit) | Runs continue; operators cannot see them |
| **Agent security / identity** | User, agent, and Runtime workload principals; mint after pin; revoke; no side doors | Classify; pin; loop | Fabric can run; not governed |
| **Agent evals** | Routing golden set, adversarial cases, CI release gate | Pin; start; loop | Fabric can run; cannot gate misroutes |
| **Domain capabilities** | Route rows, prompts, workflows, tools, outcomes, runtime behind activation | A second enterprise front door | That capability pauses; Fabric remains |
| **Platform controls** | Fabric contract, policy surface, evidence and eval bar | Owning every domain model and prompt | — |

### Three routers (do not collapse)

| Router | Question | Who calls it |
| --- | --- | --- |
| **Data Plane (decide)** | Which governed path / workflow / manifest? | Front Door (classify). Runtime (catalogue row at pinned version — not classify) |
| **Agent planner (inside Runtime)** | Which tool or step next? | Runtime (LLM loop or fixed workflow) |
| **Model router** | Which LLM endpoint for this inference? | Runtime (or cloud agent behind activation) |

### Autonomy patterns (who picks the next step inside Runtime)

| Mode | Name | Who decides the next step |
| --- | --- | --- |
| **0** | Single inference | Nobody — one model call |
| **1** | Autonomous | Model chooses tools until done |
| **2** | Deterministic | Designer — fixed stages (may include human gates) |
| **3** | Guided | Designer outer stages; model inside an allowlist |

### Invariants of the idea

1. **Four jobs.** Front Door entitles, pins, starts. Data Plane classifies. Control Plane is control UI. Runtime runs.
2. **Only `route` starts work.** Clarify / abstain never pin.
3. **Jobs name the route.** Skip classifier; do **not** skip entitle.
4. **Three principals.** User ≠ agent (software acting) ≠ Runtime workload.
5. **Channels never dial the activation target.** Front Door is the only way in.
6. **Pin first, then mint the agent token.** Do not widen scopes mid-session; new route → new freeze.
