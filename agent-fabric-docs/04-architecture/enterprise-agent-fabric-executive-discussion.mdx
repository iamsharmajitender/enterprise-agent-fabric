# Enterprise Agent Fabric — Executive discussion brief

**Purpose:** One room document for leadership — architecture, one request swimlane, what the Fabric solves, the decision ask, and who owns what. This page stands alone.

**One-line proposition:** One front door → central security, governance, audit, observability, and evaluation → many domain-owned specialised AIs.

---

## Executive summary

- **Problem:** AI is moving from pilots to a portfolio of acting capabilities. Without a common operating model we face duplicated platform work, inconsistent controls, and governance risk.
- **Proposal:** Build an Enterprise Agent Fabric — one governed front door that applies central security, policy, audit, and observability while domains retain specialised AI and data.
- **Decision requested:** Approve a V1 reference pilot (about 3 months) with an executive sponsor, funding for platform/security engineering, and success metrics (sample: onboard 3 domains; &lt;2 weeks to onboard a capability; 90% central audit coverage).

---

## 1. Architecture (what we are building)

One governed ingress. Chat and jobs enter only through **Agent Fabric Front Door**. The **Agent Fabric Plane** (Control Plane + Data Plane + Capability Registry) decides the path. **Agent Fabric Runtime** does the work. **Shared** holds Memory, RAG, and Tools. **Audit** and **Observability** sit under every run.

Channels never dial domain runtimes. Users do not pick chatbots. High-risk paths do not get side doors. Centralise controls; keep intelligence in domains.

| Shared | Memory · RAG · Tools / PEP | Session memory, retrieve, dual-checked actions |
| Evidence | Audit · Observability · Dashboard | Prove what happened; operate the fleet |

## 2. One request (chat and jobs — same path)

Every request — interactive chat or automated job — follows the same Fabric path:

1. **Ask** — User or system calls the enterprise Front Door.
2. **Verify** — Fabric confirms identity and entitlement (claims ∩ channel; chat also requires chat-visible).
3. **Route** — Intent is decided under policy (`route` / `clarify` / `abstain`). Jobs name the route explicitly: no classifier contest, no clarify — missing claims **fail closed**.
4. **Freeze & start** — Only on `route`: pin version + agent identity, async-start Runtime. Chat gets a slim reply (no routing internals). Jobs get `202` + correlation id.
5. **Execute** — Domain AI runs with approved knowledge and tools under the freeze.
6. **Control & audit** — Pause, approval, or hand-off for high-risk actions; outcome returned; evidence retained.

Clarify and abstain **never** start work. Chat sockets and job bursts use the same contract; at production scale they are separate Front Door fleets so one cannot take the other down.

## 3. What it solves

### Why leadership should care

AI is now **production capability** — it acts on customer data, money, and regulated processes. If every division builds its own entry point, security model, approval path, and audit trail, we do not get more innovation. We rebuild the same enterprise plumbing many times — with different standards, different gaps, and no single place to answer hard questions when something goes wrong.

The Fabric makes the **safe path the easy path**.

### Why now

AI is moving from **answering questions** to **taking action**. A standalone chatbot can live with light controls. A portfolio of AI that acts on behalf of the business cannot. The window to set the operating model is **before** the portfolio outgrows our ability to govern it.

### Problem today

Capabilities emerge independently (employees, customers, partners). Each team solves the visible assistant and often rebuilds the invisible work: who can access it, how requests are directed, what the AI may do, how actions are approved, and how we prove what happened.

The organisation cannot consistently answer:

- **Who** was allowed to use this AI?
- **What** was it permitted to do?
- **Why** was this capability chosen, and what did it actually do?

It also lacks controls that should exist **once** for the whole portfolio: one audit trail, one operational view, one security model, one kill switch, one approval path, one release bar.

### Proposal

Build an **Enterprise Agent Fabric** — one governed front door that applies central security, policy, audit, and observability while **domains retain** specialised AI, knowledge, and outcomes.

### What the Fabric standardises

| Control | Outcome |
| --- | --- |
| **Security** | Identity, entitlement, least-privilege for users and agent principals |
| **Governance** | Policy, approval gates, and rules for high-risk actions |
| **Audit** | Evidence of who asked, what was decided, what ran, who approved |
| **Observability** | Central ops view and alerts across capabilities |
| **Evaluation** | Pre-release checks (routing goldens, adversarial cases) before ship |

### What domains keep

- Business problems, domain knowledge, models, and outcomes
- Freedom to choose runtime and specialist logic while integrating with the Fabric contract (activation target behind the Front Door)

> Centralise controls. Keep intelligence in domains.

### Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Data privacy | Restrict data flows; least-privilege; data minimisation |
| Unsafe model behaviour | Pre-release evaluation; canarying; human-in-the-loop for risky flows |
| Latency / UX impact | Measure policy gating overhead; fast-paths for low-risk actions |
| Operational cost | Shared platform reduces duplicated spend; budget observability and SRE |

### Success measures (sample KPIs)

| KPI | Example target |
| --- | --- |
| Domain capabilities onboarded in pilot | 3 |
| Time to onboard a capability | &lt; 2 weeks |
| Central audit coverage of actions for onboarded capabilities | 90% |
| Duplicated control components removed | ≥ 3 |
| Mean time to revoke a capability | Minutes, not days |

### Roadmap (V1 pilot → scale)

| Phase | Timing | Focus |
| --- | --- | --- |
| **Phase 0** | Weeks 0–2 | Executive sponsor, success metrics, pilot domains selected |
| **Phase 1** | Weeks 3–12 | V1 reference Fabric (ingress, entitlement, routing, audit schema, basic observability); onboard 1–3 pilot domains |
| **Phase 2** | Months 3–9 | Harden controls; evaluations and approvals; scale onboarding; automate evidence exports for compliance |

**Owners:** Enterprise platform (build & run) · Domain teams (onboard & own outcomes) · Risk & governance (policy & evidence requirements).

### Proof the model works

A reference implementation already demonstrates: message → classify → entitlement → pin → execute → response, with capability registry, routing, audit foundations, and observability. That is the pilot baseline to harden, not a greenfield invent.

## 4. Roles and responsibilities (by component)

| Component | Owns | Does **not** own | If it dies |
| --- | --- | --- | --- |
| **Chat / channel frontends** | UI, chips, slim replies | Route table, tools, policy enforcement | That UI down; API path still works |
| **Agent Fabric Front Door (AFD)** | Only public ingress. Authenticate, entitle, call decide, **freeze** route pin, **async-start** Runtime, slim chat / `202` jobs. Two fleets at scale (Chat + API), one contract. | Classify logic; agent loop; catalogue UI | Chat fleet down ≠ jobs fleet down (at scale) |
| **Agent Data Plane (ADP)** | Versioned catalogue + **decide** (`route` / `clarify` / `abstain`). Eligible set = claims ∩ channel. Eval golden surface for misroutes. Serves pinned catalogue row to Runtime. | Pin; start Runtime; tool invoke | Classify fails closed — no silent start |
| **Agent Control Plane (ACP)** | Operator catalogue **UI** / control surface; policy and version visibility for humans | Hot-path decide; start Runtime; channel traffic | Operators blind; in-flight runs continue |
| **Agent Fabric Capability Registry** | Immutable published capabilities `id@version`. Manifests Runtime hydrates at pin. Agent-start tools point at API Front Door, not callee Runtime URLs. | Decide; pin; permit at tool invoke | New runs cannot hydrate; in-flight pins keep schemas |
| **Agent Fabric Runtime (AR)** | Pin hydrate, Patterns 0–3 (single inference → autonomous → deterministic → guided), call Shared. Workload identity ≠ user ≠ agent robot. May be Fabric Runtime **or** another activation (for example a Bedrock Agent) behind the pinned activation target. | Channel ingress; re-decide against live `active`; widen scopes after freeze | Controlled error after accept — not a fake success |
| **Shared — Memory** | Short / long-term memory keyed by session | Ingress classify | Runs degrade; routing still works |
| **Shared — RAG** | Corpus retrieve for grounding | Ingress classify | Grounding degrades; routing still works |
| **Shared — Tools / PEP** | Actions scoped by pinned manifest. **Dual check:** user entitlements (or approval) **and** agent scopes | Route choice; mint freeze | Side effects stop |
| **Agent Audit (data + control)** | Append-only evidence chain; examiner view by correlation id. Default-deny raw utterance, claims, and tokens in payloads. | Block the hot path; replace ops dashboards | New events may drop (fail-open); runs continue |
| **Observability** | Traces, metrics, logs across Front Door, Plane, Runtime, Shared | Compliance evidence store (that is Audit) | Runs continue; operators cannot see them |
| **Agent security / identity** | User, agent, and Runtime workload principals; mint after pin; revoke; no side doors | Classify; pin; loop | Fabric can run; not governed |
| **Agent evals (platform)** | Routing golden set, adversarial cases, CI release gate | Pin; start; loop | Fabric can run; cannot gate misroutes |
| **Domain teams** | Route rows, prompts, workflows, tools, domain outcomes, choice of runtime behind activation | Building a second enterprise front door | That domain capability pauses; Fabric remains |
| **Platform / Risk** | Fabric build & run; policy and evidence requirements; eval release bar | Owning every domain model and prompt | — |

### Three routers (do not collapse)

| Router | Question | Who calls it |
| --- | --- | --- |
| **Data Plane (decide)** | Which governed path / workflow / manifest? | Front Door (classify). Runtime (catalogue row at pinned version — not classify) |
| **Agent planner (inside Runtime)** | Which tool or step next? | Runtime (LLM loop or fixed workflow) |
| **Model router** | Which LLM endpoint for this inference? | Runtime (or cloud agent behind activation) |

### Autonomy patterns (who picks the next step inside Runtime)

| Mode | Name | Who decides the next step |
| --- | --- | --- |
| **0** | Single inference | Nobody — one model call |
| **1** | Autonomous | Model chooses tools until done |
| **2** | Deterministic | Designer — fixed stages (may include human gates) |
| **3** | Guided | Designer outer stages; model inside an allowlist |

### Locked operating rules (for the room)

1. **Four jobs.** Front Door entitles, pins, starts. Data Plane classifies. Control Plane is control UI. Runtime runs.
2. **Only `route` starts work.** Clarify / abstain never pin.
3. **Jobs name the route.** Skip classifier; do **not** skip entitle.
4. **Three principals.** User ≠ agent (software acting) ≠ Runtime workload.
5. **Channels never dial the activation target.** Front Door is the only way in.
6. **Pin first, then mint the agent token.** Do not widen scopes mid-session; new route → new freeze.
