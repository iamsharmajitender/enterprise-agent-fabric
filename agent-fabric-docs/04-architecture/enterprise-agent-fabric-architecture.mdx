# Enterprise Agent Fabric

**Agent Fabric Front Door (AFD) · Agent Fabric Plane · Agent Control Plane (ACP) · Agent Data Plane · Agent Fabric Runtime (AR) · Shared**

One fabric. One front door. One agent plane. Specialised agents underneath.

**Status:** Draft — aligned to running v1 software and production target  
**Date:** 2026-09-02  
**Behaviour source:** [status](../../02-understand/status.md) · **Executive brief:** [Enterprise Agent Fabric V1](./enterprise-agent-fabric-pitch.mdx) · **Quick deck:** [Executive quick deck](./enterprise-agent-fabric-executive-deck.mdx)

Local architecture paper. How-to stays in playbooks and box packs. This page is the working design: one decide contract, two AFD fleets at scale. APIs, fleets, and scale live on the child pages.

> **Naming.** These packs use **AFD**, **ACP**, **AR** (Agent runtime). Diagrams label the runtime **Agent runtime**; some editorial sources may still say NAFD until redrawn.

**Pin split:** Agent Front Door **calls** the Agent Data Plane (catalogue + classify). Agent Control Plane is the sibling control box. AFD **pins** `route_id` + versions and async-starts AR. Playbooks still put the pin on the ACP. Treat this page as the proposal until they catch up.

**AFD split:** one **contract** (entitle, classify, freeze, start). Two **fleets** at production scale: Chat AFD (BFF, Chat/UI) and API AFD (HTTP; Kafka job ingest is this AFD). Kafka `{runs_topic}` is AR return, not a third AFD. **Local v1:** chat and jobs share one Front Door process on port 3005 — same contract, not yet separate fleets.

| Playbooks | This paper |
| --- | --- |
| Front door | **[AFD](./agent-fabric-front-door.mdx)** — entitles, freezes, starts. Only way in. |
| Intent router | **[Agent Fabric Plane](./agent-fabric-plane.mdx)** — AFD calls **Agent Data Plane** (catalogue + classify). **ACP** is the control box. Does not do the work. |
| Agentic app | **[AR](./agent-fabric-runtime.mdx)** — specialised agents underneath. Pin, hydrate, LangGraph loop. |
| Memory / RAG / tools | **Shared** — called from AR. Not inside AR. |
| Tool manifests | **[Agent Fabric Capability Registry](./agent-fabric-capability-registry.mdx)** — sits with Agent Fabric Plane. Publishers append `id@version`. AR hydrates at pin. Agent-start `invoke` is API AFD. |

## 1. Job of the system

Two AFD fleets (production) and one **Agent Plane** per **trust domain**. Every turn is entitled, decided, and (on `route`) async-started into AR. Users do not pick chatbots. Channels never dial Legal or payments URLs.

**Today (typical enterprise):** users open Finance, then HR, then Legal chatbots. Partner APIs invent dispatch. Not everyone should see Legal.

**Target:** Chat/UI hits the Chat AFD. Partners, systems, and Kafka job starts hit the API AFD. That AFD calls the **Agent Data Plane** to decide which governed path owns this turn. On `route`, the **AFD** pins it and starts AR.

Agent Data Plane classifies against the route/workflow catalogue. ACP is the control box in the same Agent Plane. The **Agent Capability Registry** sits next to those two boxes. AR does the work (Memory, RAG, Tools via **Shared**). AFD freezes and starts. The two AFDs share that contract and that Agent Plane. They do not share a process.

| With one shared Agent Plane | Without |
| --- | --- |
| One ingress decision for a shared experience | Each UI or `if/else` guesses the agent |
| Two AFD fleets, one contract | Chat SSE and jobs share a process, or Kafka is a third start |
| One versioned route/workflow catalogue + audit | Fragmented tables, inconsistent entitlements |
| One eval surface for misroutes | Cannot gate routing quality in CI |
| Clarify / abstain / safety in one place | Side doors into high-risk agents |

**Scope:** one Agent Plane per shared UX / trust domain. Not one mega-agent. Routes stay specialised. AFDs are separate fleets so chat sockets cannot take down job start, and the reverse.

| Audience | Cares about |
| --- | --- |
| End users | One assistant, slim replies, no routing internals |
| Platform | Chat AFD + API AFD (pin + start, separate fleets), Agent Plane (ACP + data plane), Shared, eval CI |
| Domain teams | Route rows and agent behaviour behind `activation_target` |

## 3. Non-functional requirements {#nfrs}

**Decide SLO** and **run SLO** are different numbers. An AFD module may sit next to Agent Plane while the domain is small. The two AFDs may not: UI BFF and jobs must not share a process (FR-9). Decide must not wait on a 12-step loop. Chat sockets must not wait on job bursts.

| Concern | Decide path (AFD + Agent Plane) | Run path (AR) |
| --- | --- | --- |
| **Latency** | p99 entitle + classify + pin + start-ack. Layer ② &lt;50ms. Decide+pin+`202` p99 &lt;100ms. Pattern 0 is the only sync wait. | Loop may take seconds to minutes. Not on the decide clock. |
| **Availability** | ACP accepts turns if one AR is down. One AFD down does not take the other (FR-9). | Controlled error after `202`. Not a fake success. |
| **Correctness** | Adversarial routing cases pass at 100% before release. Golden set in CI. | PEP, pattern budgets, tool allowlists (not this page). |
| **Durability** | Decision record is async. Decide does not wait for audit commit. | Run pin is durable. |
| **Security** | No public Agent Plane URL. Empty eligible set: do not start. Fail closed. | Tools and PEP run only after the freeze. Dual check: user + agent. Shared is not a side door. AR workload identity is not the API caller. |
| **Consistency** | AFD freeze: `route_id` + versions + `activation_target` + `agent_client_id` + `correlation_id`. | AR copies that freeze. Pin miss: AR API, not AR DB. |

| Assumption | Working target |

## 4. High-level architecture

**Enterprise Agent Fabric** is the outer box. **Agent security** and **Agent evals** sit on the left. **Events** sits at the top. Agent Front Door, Agent Control Plane, and Agent Runtime emit into Events. Left to right: **Agent Front Door**, **Agent Plane** (ACP stacked on Agent Data Plane, Agent Capability Registry beside them), **Agent Runtime**, **Shared** (Memory, RAG, Tools). Do not collapse them. A small database mark on Front Door, Agent Plane, and Runtime means each owns a store (frozen route/session, catalogue, runs). AFD is two fleets with one contract (Chat BFF and API, including Kafka ingest). AFD, Agent Plane, AR, and Shared emit into Observability. **Observability** and **Agent audit** sit side by side. Both feed **Dashboard**. Dashboard feeds **Responsible / Governed AI**.

**Agent Front Door calls the Agent Data Plane to classify.** The data plane does **not** call or start AR. After `outcome=route`, the **Front Door** pins the frozen route/session (`route_id` + versions), then async-starts **Agent Runtime** on a straight start. **AR fetches** the catalogue row and manifest pointers from the Agent Data Plane at that pinned version, **hydrates** each capability from the **Agent Capability Registry** (same Agent Plane band, not Shared), copies the run pin, and returns `202` plus `correlation_id` to the Front Door. **Memory**, **RAG**, and **Tools** sit in **Shared**.

### Three routers (do not collapse)

| Router | Question | Who calls it |
| --- | --- | --- |
| **Agent Data Plane** | Which workflow / manifest / app? | Agent Front Door (classify). AR (catalogue row at pinned version, not classify) |
| **Agent planner** (inside AR) | Which tool / step next? | AR (Pattern 1 LLM loop or Pattern 2/3 workflow) |
| **Model router** | Which LLM endpoint for this inference? | AR |

### Autonomy patterns (inside AR)

`autonomy_mode` answers **who picks the next step** inside AR — not how the run is started. Full contracts: [06-patterns](../../06-patterns/README.md).

| Mode | Name | Who decides |
| --- | --- | --- |
| **0** | Single inference | Nobody — one LLM call |
| **1** | Autonomous | LLM `CALL` / `DONE` over a manifest |
| **2** | Deterministic | Workflow designer — fixed stages, branch, `human_gate` |
| **3** | Guided | Designer stages; LLM inside an allowlist |

Orthogonal attachments — retrieval, memory, `kind=agent` child jobs, checkpoint resume — compose beside the mode. They are not a fifth pattern.

### Human and specialist composition

Three human shapes and one specialist shape are first-class in the catalogue:

| Shape | Mechanism | Run behaviour |
| --- | --- | --- |
| **Process gate** | Workflow `human_gate` | Run pauses (`waiting`); resume via `/turns` with approval packet |
| **Async handoff** | Domain tool `escalate_to_human` | Ticket opened; parent completes when handoff succeeds |
| **LLM signal** | Structured `human_review_*` in notes | No pause — evidence for a later branch |
| **Specialist child** | `kind=agent` capability | Parent AR POSTs API AFD `/v1/jobs`; optional join waits for child result |

### Data: route pin vs run pin

Two records. Field dictionary: playbooks session custody.

| Record | Who writes it | Lives where | Job |
| --- | --- | --- | --- |
| **Frozen route/session** | Agent Front Door (AFD) | AFD store, keyed by `session_id` or `job:{idempotency_key}`, TTL | Pinned route (`route_id`, versions, `activation_target`, `agent_client_id`, `correlation_id`) |
| **Decision** | Agent Control Plane (ACP) | Audit store (target) | Why this turn routed, clarified, or abstained |
| **Route/workflow catalogue** | Platform / domain teams | Agent Data Plane | Versioned rows the data plane classifies over. Includes `agent_client_id` per row. |
| **Run pin** | AR | Durable run store | Copy of those versions plus loop checkpoint, token reference, `run_id` |

The AFD stores the **frozen route/session** so `"yes"` or a jobs retry keeps the same `route_id` and versions. Pin miss: **AR API**, not AR Postgres. `session_id` is the chat thread.

### Three principals (do not collapse) {#three-principals}

AR is the executor. It is not the agent. Shared AR is a compute choice. Identity lives on the pinned route.

| Principal | Answers | Issued / held | On the wire |
| --- | --- | --- | --- |
| **User** | Who is asking? | AFD: IdP token, `sub`, `emts` | Claims or approval id. Not the tool-call bearer. |
| **Agent** | Which software is acting? | Catalogue `agent_client_id` (e.g. `payments-agent-v2`). After freeze: IdP token for that client, downscoped to this route. | `Authorization` bearer on Shared Tools calls |
| **AR workload** | Which box is running the loop? | Platform: pod identity to Shared, IdP, model router | Workload auth to fabric internals. Not a downstream API principal. |

`activation_target` isolates the **box** (PCI, release, network). `agent_client_id` names the **robot**. Omit `activation_target` and routes share AR compute. They do not share one agent bearer. A new use case is a new catalogue row and a new `agent_client_id`, not a new AR.

Mint order: **pin first, then agent token.** Route change mid-session: new downscoped token. Do not widen the existing one. Jobs use the same robot badge; only how you carry the user changes (live claims vs stored approval). Dual check is Shared Tools / PEP: may this person, and may this robot.

## 5. Request path

The Agent Data Plane **classifies**. Agent Front Door **calls it**, then **freezes and starts**. AR **fetches the row** at the pin, **hydrates**, then **runs**. `202` comes from AR, not from the data plane.

**Chat / generic turn**

1. AFD authenticates. Mint or reuse `session_id`.
2. Frozen route/session + continuation (`"yes"`, `"$500"`): skip classify, resume AR.
3. Else Agent Front Door calls the Agent Data Plane (message + claims + `session_id`).
4. Data plane: eligible = catalogue ∩ claims ∩ channel. Returns `route` / `clarify` / `abstain`. Writes the decision record (target). Does not pin or start.
5. `clarify` / `abstain`: talk to the user (jobs: fail closed or `escalate_human`). No AR. After a pick, back to step 3.
6. `route`: AFD stores the freeze (`route_id` + versions + `activation_target` + `agent_client_id`), `POST`s AR.
7. AR fetches the catalogue row and manifest pointers from the Agent Data Plane at that pinned version, hydrates from Registry, copies the run pin, requests a token for the pinned `agent_client_id`, returns `202 { "correlation_id" }`. Nobody re-reads `active`.
8. AFD returns slim UI payload, or `202` to the jobs caller. Shared Tools / PEP dual-checks user + agent on every call.

**API AFD:** caller already named `route_id`. Skip classifier and clarify. Still entitle and record (step 4), then freeze + start (steps 6–8). `{runs_topic}` is not this path.

## 6. Isolation and shed {#isolation-and-shed}

| Failure | Agent Front Door (AFD) | Agent Control Plane (ACP) |
| --- | --- | --- |
| One AR down | Other `activation_target`s still start. That route returns a controlled error after `202` or on start-ack timeout. | Still accepts new turns. |
| One AFD down | The other ingress still works. | Unaffected. |
| Frozen-route/session store down | Continuations degrade to open-run on AR. New `route` can still start if start-ack works. | Unaffected. |
| Catalogue unreadable | Do not start. | Fail closed. |
| Shared down | Routing still works. AR degrades (no memory / RAG / tools). | Unaffected. |
| Layer ③ saturated | Serve `clarify` / `abstain`. | Do not enqueue behind Layer ②. |
| Audit lag | Decide still succeeds. | Exam trail lags. |

### Anti-patterns

- Freeze in replica memory (the next `"yes"` lands on another replica and misses the pin).
- One autoscaler for AFD + Agent Plane + AR workers.
- One process or autoscaler for UI BFF and jobs URL (FR-9) in production.
- Public Agent Plane URL (then you scale auth, OpenAPI, and slim UX into Plane ①).
- Kafka ingest as a third public ingress, or `{runs_topic}` as a job start.
- Caller waits for the memo (decide SLO dies).
- Scaling Layer ② by adding Layer ③ replicas.
- Putting event-only rows on chat chips to "reduce classify load" (that is a side door, not a scale tactic).
- Re-reading `active` after pin (wrong, and it also adds origin QPS).
- AR `POST`s another AR's `activation_target` (A2A skips API AFD).
- AR workload identity as `Authorization` to downstream APIs (AR becomes a fat `svc-agents`).
- One agent token at AR boot with every route's scopes.
- A new `activation_target` per route only to get a different identity (that inflates fleets to fix a token problem).
- Deriving `agent_client_id` from `route_id` instead of pinning an explicit pointer.
- The user bearer as the tool-call caller, or skipping the agent check because AFD already entitled the user.

## 7. What examiners and operators should be able to show

1. Which `route_table_version` was active for this session.
2. Which routes were eligible for this identity (and which were hinted).
3. Why this turn routed, clarified, or abstained (`router_layer`, confidence).
4. That adversarial routing cases pass at 100% before release.
5. That a routing incident was added to the golden set and blocked in CI.
6. That jobs HTTP and Kafka ingest still have a Plane ① decision record (explicit `route_id` is not a skip).
7. Which `agent_client_id` was frozen for this run, which agent called this tool, and that user and agent both passed (FR-10).
8. Which human shape fired — gate, handoff, or signal — and whether the run paused or completed.

## Non-goals

- One mega-agent with every tool.
- One AR bearer for every route (shared compute is not a shared robot).
- The user token as the tool-call caller.
- One process or autoscaler for chat SSE and jobs start in production (FR-9).
- Browser, partner, or domain MS calling the Agent Plane or AR directly.
- Kafka as a third public ingress into the Agent Control Plane.
- `{runs_topic}` as a job start.
- ACP waiting on Temporal / the 12-step loop.
- Event-only routes shown as chat chips.
- Entitlements stored per user in the route table (use ingress claims).

## Appendix: decisions locked

FRs above are the testable form.

1. **Four jobs.** AFD (entitle, pin, start), Agent Data Plane (classify + catalogue; called by AFD), ACP (control + audit), AR (run pin + LangGraph loop; requests agent token). Pin sits on AFD. Agent Capability Registry sits with Agent Plane. Memory, RAG, and Tools sit in Shared.
2. **Two AFD fleets, one contract.** Separate process (FR-9). Shared Agent Plane. `{runs_topic}` is return. Kafka job start is the API AFD.
3. **Jobs name the route.** Skip classifier and clarify. Do not skip Plane ①.
4. **Generic chat still classifies.** Hints are eligible + chat-visible. A tap is Layer ①.
5. **Clarify / abstain never start AR.** On `route`: freeze, async-start, `202`.
6. **One Agent Plane per trust domain.** Control Plane and Data Plane stay separate boxes. Not one mega-agent.
7. **Three principals.** User, agent, AR workload. Catalogue `agent_client_id` on the freeze. Pin first, then mint. Dual check in Shared Tools / PEP. Shared AR is compute, not identity (FR-10).
8. **Capabilities are references.** Publishers append `id@version` next to Control Plane and Data Plane. Manifests refer. AR hydrates the whole pinned manifest before the LLM. `kind=agent` `invoke` is API AFD jobs, not the callee AR.
